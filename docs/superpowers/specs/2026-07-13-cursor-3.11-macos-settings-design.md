# Cursor 3.11 macOS Settings Localization Design

## Summary

Add complete, recoverable localization support for Cursor 3.11.13 on macOS
ARM64 while preserving the repository's existing cross-platform behavior. The
change focuses on Cursor-owned Settings and related UI surfaces that the
official VS Code Simplified Chinese language pack does not translate.

The implementation must localize the real Cursor 3.11 Settings React UI,
remain responsive during repeated React renders, protect technical and
user-authored content, install through an all-or-nothing transaction, coexist
with verifiable third-party patches, and restore only this tool's changes.

## Goals

- Support Cursor 3.11.13, commit
  `3f21b08f0b436a07be29fbfe00b304fa15553350`, on macOS ARM64.
- Resolve a Cursor installation from `Cursor.app`, `Contents`,
  `Contents/Resources/app`, and the existing Windows/Linux entry forms.
- Translate Cursor Settings, Agents-related surfaces, model framing UI,
  Tools & MCPs, Rules/Skills/Subagents, Browser & Network, menus, popovers,
  dialogs, tooltips, and safe attributes.
- Preserve official VS Code localization and all protected technical,
  project, user, chat, Agent-output, code, command, and log content.
- Provide read-only `--check`, `--status`, and `--dry-run` diagnostics.
- Apply all file changes atomically with a versioned manifest and roll back the
  complete transaction after any failure.
- Restore only changes recorded by this tool and reject stale or ambiguous
  restores.
- Preserve and coexist with verifiable ccursor, Cursor++, BYOK,
  cursor-always-local, renderer-hook, and checksum patches.
- Produce repeatable unit, runtime DOM, smoke, syntax, coexistence, rollback,
  and real macOS UI evidence.

## Non-Goals

- Do not copy a workbench bundle from an older Cursor release.
- Do not modify or replace the official VS Code language pack.
- Do not translate model names, provider names, extension names, repository
  names, custom Rules/Skills/Subagents names, or user-authored content.
- Do not read Cursor tokens, email addresses, `state.vscdb`, authentication
  data, or account databases.
- Do not add usage monitoring or call Cursor account APIs.
- Do not attempt to recreate Cursor's Apple Developer ID signature.
- Do not disable SIP, remove `com.apple.macl`, bypass Gatekeeper, or recommend
  broad permission changes such as `chmod -R 777`.
- Do not automatically create or submit a pull request.

## Verified Cursor 3.11.13 Runtime Structure

The design is based on inspection of the live Cursor 3.11.13 renderer through
Cursor DevTools, not inferred selectors.

- Cursor Settings is mounted in the main
  `out/vs/code/electron-sandbox/workbench/workbench.html` document.
- The observed Settings surface is light DOM. It is not hosted in an iframe or
  webview, and no Shadow Root is present on the inspected Settings path.
- React renders both hashed `glass-*` classes and stable
  `cursor-settings-sidebar-*` classes.
- The visible `General` label was observed in two separate nodes: a regular
  heading span and a sidebar span with
  `class="cursor-settings-sidebar-cell-label"` and `title="General"`.
- The sidebar contains stable labels such as `Agents`, `Cloud Agents`,
  `Models`, `Git & PRs`, `Rules, Skills, Subagents`, `Tools & MCPs`, and
  `Browser & Network`.
- The page includes a Settings search control whose accessible text is
  `Search Settings`.

Hashed `glass-*` class names are therefore not valid compatibility anchors.
Runtime detection will use stable Settings sidebar classes, the Settings
search control, roles, and their shared React surface. The implementation will
capture additional DOM fixtures from the same runtime before finalizing the
classifier.

## Architecture

### CLI Facade

`CursorTranslate.py` remains the user-facing entry point and preserves the
existing apply, restore, extraction, and legacy-cleanup commands. It owns
argument parsing, human-readable reporting, and orchestration only.

It delegates new behavior to focused modules:

- `cursor_translate/bundle.py`: path resolution, bundle metadata, required
  resource discovery, checksum lookup, process detection, and read-only
  preflight reporting.
- `cursor_translate/dictionary.py`: dictionary parsing, comments, duplicate
  and conflict validation, and runtime payload construction.
- `cursor_translate/transaction.py`: manifest lifecycle, staging, atomic
  writes, rollback, verified local-patch restore, and backup retention.
- `cursor_translate/runtime.py`: combines the runtime JavaScript template with
  the validated dictionary and bounded regular-expression rules.
- `cursor_translate/runtime_template.js`: DOM classification, translation,
  observation, batching, and test hooks with no embedded account data.

Existing public helpers imported by current tests remain as compatibility
wrappers until their callers and tests move to the focused modules. Candidate
extraction and legacy language-pack cleanup remain in the CLI module unless a
direct dependency requires a small move.

### Bundle Model

`CursorBundle` is an immutable structure containing:

- the normalized `resources/app` path;
- Cursor version and commit;
- paths to `workbench.html`, `workbench.desktop.main.js`, `product.json`,
  `nls.messages.json`, and `main.js`;
- the workbench checksum key and current value;
- detected tool marker and foreign-patch evidence;
- the planned write set.

Path resolution may return a candidate only after `product.json` identifies a
Cursor bundle. Full preflight validates every required path and anchor before
the write transaction begins. A future layout change must fail with a specific
missing-path or missing-anchor diagnostic and zero target-file writes.

### Runtime Translation Context

Each candidate node is classified before lookup:

1. `cursor-settings`: Cursor-owned Settings navigation and content.
2. `vscode-settings`: Monaco/VS Code settings surfaces handled by the official
   language pack.
3. `model-provider-picker`: model and provider choices plus surrounding UI.
4. `cursor-command-ui`: safe Cursor menus, popovers, dialogs, tooltips, and
   segmented controls.
5. `protected-editor`: editor, terminal, diff, code, command, path, and log
   surfaces.
6. `protected-conversation`: chat history, Agent output, tool output, and
   user-authored Rules/Skills/Subagents names.
7. `protected-input`: editable controls, current values, and contenteditable
   regions.

The `cursor-settings` classifier is rooted by the verified stable Settings
signals and their shared mounted surface. It must not classify arbitrary text
that merely contains the word `Settings`. The `vscode-settings` classifier
takes precedence so Cursor-specific translation never rewrites officially
localized VS Code settings.

Model and provider option text is protected. Framing text such as a menu title
or explanatory sentence may still translate. `Auto`, `High`, `Low`, `None`,
and similar enums are protected inside model/provider and technical contexts,
but may translate when the node is a verified natural-language setting label.

### Mutation Processing

The runtime performs an initial scan and observes:

- added element and text nodes;
- text-node `characterData` changes;
- `title`, `aria-label`, `placeholder`, `aria-placeholder`, and
  `aria-description` changes;
- newly attached open Shadow Roots discovered during traversal.

The current Cursor Settings path does not use Shadow DOM. Open Shadow Root
support is a bounded compatibility feature; closed roots are inaccessible and
iframe/webview documents remain outside the translator. These boundaries are
reported honestly rather than bypassed.

Mutations are deduplicated into a bounded queue and processed within a per-frame
node budget. A source-value/applied-value record prevents self-triggered
rewrites. If React later writes English back into the same node or attribute,
the changed source value is eligible again. Chinese output and unchanged
values are no-ops, preventing translation loops.

### Dictionary Rules

`cursor_translate_dic.txt` retains its current `"source" => "translation"`
format. Blank lines and `#` or `//` comments remain supported. New Cursor 3.11
entries are grouped by Settings page or feature.

Parsing fails on:

- duplicate keys, including duplicates with the same translation;
- conflicting translations for one source key;
- empty keys or values;
- malformed separators or quoting;
- normalized keys that would ambiguously override one another.

Dynamic regular expressions remain in code, are anchored, and have narrow
capture groups. They cover finite numeric/status forms only. No expression may
match arbitrary sentences, code, paths, URLs, commands, or user content.

The source-string extractor remains advisory. It never writes the dictionary.
Cursor 3.11 candidates are manually selected from confirmed user-visible UI;
internal identifiers, telemetry keys, stack strings, paths, and source-only
messages are rejected.

## Read-Only Diagnostics

`--check` and `--dry-run` run the same complete preflight used by apply but do
not create probe files, temporary files, manifests, backups, or target writes.
They report:

- normalized Cursor path, version, and commit;
- all resolved required files;
- checksum key and whether it is present;
- injection-anchor count and validity;
- current tool marker and manifest state;
- known and unknown conflicting patch evidence;
- whether Cursor is running;
- write-permission metadata;
- the exact planned write set.

`--status` reports whether a valid manifest exists, whether its Cursor version
and commit match the current bundle, whether each recorded patch is present,
and whether external drift prevents restore. It is also read-only.

Read-only permission reporting uses filesystem metadata and `os.access`; it
does not claim that a later atomic replace is guaranteed. Apply confirms actual
staging-file creation only after all other preflight checks pass and as the
first step of the controlled transaction.

## Transaction and Manifest

### Backup Location

Backups live outside Cursor.app in a tool-owned user-data directory. On macOS:

```text
~/Library/Application Support/cursor-v3-chinese-translate/backups/
```

Windows and Linux use their normal per-user application-data locations. A
bundle identity derived from the normalized application path and product
metadata separates multiple installations. Each apply receives a random
manifest id and its own directory.

### Manifest Content

The JSON manifest includes:

- schema version, tool name, and tool version;
- manifest id and creation time;
- normalized bundle identity;
- Cursor version and commit;
- every touched path stored relative to `resources/app`;
- original and applied SHA-256 values;
- backup filename and backup SHA-256;
- the exact reversible local patch description;
- pre-existing known patch evidence;
- transaction status: `prepared`, `applying`, `applied`, `rolling_back`,
  `rolled_back`, `restoring`, or `restored`.

No token, email, user database value, environment dump, or arbitrary command
line is recorded.

### Apply State Machine

1. Resolve the bundle and build the complete read-only preflight report.
2. Reject a running Cursor process, missing resource, missing checksum key,
   ambiguous injection anchor, stale active manifest, or unsafe conflict.
3. Generate all final bytes in memory, including the final checksum, and
   validate generated JavaScript with `node --check`.
4. Create the manifest directory and copy every original touched file into it.
5. Verify each backup SHA-256 and persist a `prepared` manifest atomically.
6. Stage each final file in its destination directory and fsync it.
7. Set state to `applying`, then replace target files atomically in a stable
   order. The checksum-bearing `product.json` is replaced after workbench
   content and before final verification.
8. Verify applied hashes, the injected marker, generated-script marker, and
   the product checksum.
9. Set state to `applied` atomically.

If any action after step 4 fails, the transaction enters `rolling_back` and
restores every target written by that transaction from its verified backup.
It then verifies original hashes and records `rolled_back`. A rollback failure
is reported with the exact remaining paths and preserves all recovery data.

### Restore State Machine

Restore selects only an `applied` manifest matching the current bundle
identity, Cursor version, and commit. A manifest from another Cursor version
is rejected before writing.

For each file, restore verifies the recorded applied state and reverses only
the tool-owned local patch:

- remove the exact HTML block containing tool name, version, and manifest id;
- delete `cursor_hanhua.js` only if its marker, manifest id, and hash match;
- restore the prior checksum only if the checksum still equals the value
  written by this manifest;
- reverse native-resource replacements only where the exact recorded applied
  bytes are still present.

Unrelated bytes added or modified by another tool remain untouched. If a
tool-owned patch cannot be located uniquely, restore stops before any write.
All reverse results are generated and staged before replacement, so restore is
also transactional. Full-file backups are retained for disaster recovery and
same-transaction rollback, not used to overwrite externally modified files
during normal restore.

## Third-Party Patch Coexistence

Detection recognizes this tool's marker separately from foreign marker names,
backup suffixes, injected scripts, renderer hooks, and checksum changes. It
never deletes `.bak`, `backup-*`, or similarly named foreign artifacts.

Known foreign modifications are allowed only when every planned local patch is
unique and reversible. The implementation stops when:

- another tool occupies or duplicates this tool's HTML anchor;
- the intended checksum key is missing or duplicated;
- a native-resource replacement cannot identify exact source bytes;
- an active manifest describes a different current state;
- a restore target no longer contains a unique tool-owned applied fragment.

Tests use representative `@cometix/ccursor`, Cursor++/BYOK, and
cursor-always-local markers across `product.json`, `main.js`,
`nls.messages.json`, `workbench.desktop.main.js`, and `workbench.html`.
Untouched foreign markers and backup files must be byte-identical after apply
and restore.

## Security and Privacy

The default and only mode in this change is pure localization. The tool reads
only the selected Cursor application resources, its own dictionary, and its
own backup manifests. It does not inspect Cursor user data or make network
requests.

Process detection compares process identity without printing complete process
environments or command lines. Diagnostics redact unexpected values and never
log authentication material.

Real UI acceptance uses an isolated temporary user-data and extensions
directory. It does not reuse the normal Cursor profile, account session, chat
history, workspace state, or extension state.

## Testing Strategy

All new behavior follows red-green-refactor. Each regression test is run on the
pre-change implementation or before its production implementation and must
fail for the intended missing behavior.

### Python Unit and Integration Tests

- Cursor 3.11.13 macOS bundle metadata and all supported path entry forms.
- Missing resource, missing checksum key, duplicate anchor, read-only check,
  and running-process preflight failures with zero writes.
- Dictionary duplicate, conflict, malformed-entry, comment, and normalized-key
  validation.
- Manifest creation, schema, version matching, stale-version rejection, and
  status reporting.
- Atomic apply idempotency and exact planned writes.
- Injected failure after each write boundary followed by complete hash restore.
- Restore of only this tool's changes while preserving foreign modifications.
- Exact conflict rejection when ccursor and this tool target the same fragment.
- Coexistence with representative foreign markers and backup files.

### Runtime DOM Tests

Node's test runner and a pinned DOM test dependency load the generated runtime
against checked-in Cursor 3.11 fixture HTML. Tests cover:

- Settings sidebar and content translation;
- incrementally inserted nodes;
- `characterData` updates on an existing node;
- React rewriting translated text back to English;
- title, aria-label, placeholder, aria-placeholder, and aria-description;
- menus, popovers, dialogs, tooltips, toggles, and segmented controls;
- bounded dynamic numeric patterns;
- model and provider names remaining unchanged;
- contextual handling of Auto/High/Low/None;
- user input, current input values, code, paths, commands, logs, chat history,
  Agent output, extension names, and custom names remaining unchanged;
- official VS Code Settings fixture remaining unchanged;
- repeated execution and observer callbacks remaining idempotent;
- open Shadow Root traversal and explicit iframe/webview skipping;
- queue bounds and absence of an observer rewrite loop.

### Required Commands

The final verification runs and reports:

```text
python3 -m py_compile CursorTranslate.py
python3 -m unittest -v
python3 smoke_test.py
node --check <generated cursor_hanhua.js>
```

The DOM suite and any package integrity command required by its pinned test
dependency are also run and reported.

## Real macOS Acceptance

Acceptance is performed on a recoverable copy of Cursor 3.11.13, never by
experimenting directly on the primary application. The copy starts from a
recorded state that includes representative existing third-party modifications
so coexistence is exercised.

1. Use an isolated user-data and extensions directory with no account session.
2. Record SHA-256 for `workbench.html`, `workbench.desktop.main.js`,
   `product.json`, `nls.messages.json`, and `main.js`.
3. Run `--check` and confirm no hashes or directory contents change.
4. Apply localization and verify the manifest, injected marker, generated
   script, planned writes, and product checksum.
5. Launch the copy and capture visible evidence for the Agents Window, Editor
   Window, Cursor Settings General, Agents, Models, Tools & MCPs,
   Rules/Skills/Subagents, Browser & Network, model menu, and ordinary VS Code
   Settings.
6. Verify expected Chinese labels and descriptions while model/provider names,
   code, paths, user input, and other protected content remain unchanged.
7. Exercise page switches, popovers, and a React rerender; observe CPU and
   renderer responsiveness for an abnormal observer loop.
8. Quit Cursor completely, run restore, and verify all five recorded hashes
   return to their pre-apply values while foreign artifacts remain.
9. Launch the restored copy again and verify normal operation.
10. Record `codesign --verify --deep --strict` and Gatekeeper assessment
    separately without claiming that `product.json` checksum repair restores
    Apple's signature.

Screenshots and a concise verification log are stored outside Git unless the
repository intentionally adds a small, redacted evidence directory. No user
profile, token, logs, application binaries, or machine-specific absolute paths
may enter the commit.

## Acceptance Criteria

- All required automated commands and the DOM suite pass from a clean checkout.
- Read-only modes produce zero filesystem writes.
- Every preflight failure produces zero target writes.
- Injected apply failures restore every original hash.
- Stale manifests and ambiguous conflicts are rejected before writing.
- Normal restore removes only verified tool-owned changes.
- Foreign patch markers, modifications, and backup files survive apply and
  restore byte-for-byte.
- Cursor 3.11.13 Settings and Agents-related pages visibly show the expected
  Chinese translations in real UI evidence.
- Model/provider names, VS Code localization, code, paths, commands, inputs,
  chat history, Agent output, extension names, and custom names are unchanged.
- Restore returns every targeted resource to its recorded pre-apply SHA-256 and
  the restored Cursor copy launches successfully.
- The Git diff contains no application binaries, user configuration, tokens,
  logs, screenshots with private data, or machine-specific absolute paths.
