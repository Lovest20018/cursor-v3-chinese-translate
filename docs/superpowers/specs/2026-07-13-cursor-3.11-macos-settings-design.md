# Cursor 3.11 macOS Settings Localization Design

## Summary

Add complete, recoverable localization support for Cursor 3.11.13 on macOS
ARM64 while preserving the repository's existing cross-platform behavior. The
change focuses on Cursor-owned Settings and related UI surfaces that the
official VS Code Simplified Chinese language pack does not translate.

The implementation must localize the real Cursor 3.11 Settings React UI,
remain responsive during repeated React renders, protect technical and
user-authored content, install through an all-or-nothing transaction, coexist
with verifiable third-party patches, and restore only this tool's changes.

## Goals

- Support Cursor 3.11.13, commit
  `3f21b08f0b436a07be29fbfe00b304fa15553350`, on macOS ARM64.
- Resolve a Cursor installation from `Cursor.app`, `Contents`,
  `Contents/Resources/app`, and the existing Windows/Linux entry forms.
- Translate Cursor Settings, Agents-related surfaces, model framing UI,
  Tools & MCPs, Rules/Skills/Subagents, Browser & Network, menus, popovers,
  dialogs, tooltips, and safe attributes.
- Preserve official VS Code localization and all protected technical,
  project, user, chat, Agent-output, code, command, and log content.
- Provide read-only `--check`, `--status`, and `--dry-run` diagnostics.
- Apply all file changes atomically with a versioned manifest and roll back the
  complete transaction after any failure.
- Restore only changes recorded by this tool and reject stale or ambiguous
  restores.
- Preserve and coexist with verifiable ccursor, Cursor++, BYOK,
  cursor-always-local, renderer-hook, and checksum patches.
- Produce repeatable unit, runtime DOM, smoke, syntax, coexistence, rollback,
  and real macOS UI evidence.

## Non-Goals

- Do not copy a workbench bundle from an older Cursor release.
- Do not modify or replace the official VS Code language pack.
- Do not translate model names, provider names, extension names, repository
  names, custom Rules/Skills/Subagents names, or user-authored content.
- Do not read Cursor tokens, email addresses, `state.vscdb`, authentication
  data, or account databases.
- Do not add usage monitoring or call Cursor account APIs.
- Do not attempt to recreate Cursor's Apple Developer ID signature.
- Do not disable SIP, remove `com.apple.macl`, bypass Gatekeeper, or recommend
  broad permission changes such as `chmod -R 777`.
- Do not automatically create or submit a pull request.

## Verified Cursor 3.11.13 Runtime Structure

The design is based on inspection of the live Cursor 3.11.13 renderer through
Cursor DevTools, not inferred selectors.

- Cursor Settings is mounted in the main
  `out/vs/code/electron-sandbox/workbench/workbench.html` document.
- The observed Settings surface is light DOM. It is not hosted in an iframe or
  webview, and no Shadow Root is present on the inspected Settings path.
- React renders both hashed `glass-*` classes and stable
  `cursor-settings-sidebar-*` classes.
- The visible `General` label was observed in two separate nodes: a regular
  heading span and a sidebar span with
  `class="cursor-settings-sidebar-cell-label"` and `title="General"`.
- The sidebar contains stable labels such as `Agents`, `Cloud Agents`,
  `Models`, `Git & PRs`, `Rules, Skills, Subagents`, `Tools & MCPs`, and
  `Browser & Network`.
- The page includes a Settings search control whose accessible text is
  `Search Settings`.

Hashed `glass-*` class names are therefore not valid compatibility anchors.
Runtime detection will use stable Settings sidebar classes, the Settings
search control, roles, and their shared React surface. The implementation will
capture additional DOM fixtures from the same runtime before finalizing the
classifier.

## Architecture

### CLI Facade

`CursorTranslate.py` remains the user-facing entry point and preserves the
existing apply, restore, extraction, and legacy-cleanup commands. It sets
`sys.dont_write_bytecode = True` before importing local modules, then owns
argument parsing, human-readable reporting, and orchestration only. This keeps
read-only commands from creating repository `__pycache__` files.

It delegates new behavior to focused modules:

- `cursor_translate/bundle.py`: path resolution, bundle metadata, required
  resource discovery, checksum lookup, process detection, and read-only
  preflight reporting.
- `cursor_translate/dictionary.py`: dictionary parsing, comments, duplicate
  and conflict validation, and runtime payload construction.
- `cursor_translate/transaction.py`: manifest lifecycle, staging, atomic
  writes, rollback, verified local-patch restore, and backup retention.
- `cursor_translate/runtime.py`: combines the runtime JavaScript template with
  the validated dictionary and bounded regular-expression rules.
- `cursor_translate/runtime_template.js`: DOM classification, translation,
  observation, batching, and test hooks with no embedded account data.

Existing public helpers imported by current tests remain as compatibility
wrappers until their callers and tests move to the focused modules. Candidate
extraction and legacy language-pack cleanup remain in the CLI module unless a
direct dependency requires a small move.

The modules exchange immutable values rather than independently reparsing the
bundle:

- `PreflightReport`: bundle identity, compatibility findings, process state,
  conflicts, existing installation state, and exit classification.
- `PatchPlan`: exact ordered operations, original bytes/hashes/metadata,
  resulting bytes/hashes, checksum values, and reversible fragment records.
- `ManifestValidation`: active revision, transaction state, drift category,
  and permitted recovery or restore action.

`--dry-run`, apply, and tests consume the same `PatchPlan`. Apply may reject a
plan if the target identity changes, but it may not silently rebuild different
bytes after dry-run.

### Bundle Model

`CursorBundle` is an immutable structure containing:

- the normalized `resources/app` path;
- Cursor version and commit;
- required apply paths: `workbench.html` and `product.json`;
- the planned generated path `cursor_hanhua.js`, including whether it is
  absent, tool-owned, or a conflicting foreign file;
- compatibility/read-only paths: `workbench.desktop.main.js`;
- optional native-menu paths: `nls.messages.json` and `main.js`;
- the workbench checksum key and current value;
- detected tool marker and foreign-patch evidence;
- the planned write set.

Path resolution may return a candidate only after `product.json` identifies a
Cursor bundle. For the supported Cursor 3.11.13 profile, all five packaged
resources must resolve and are reported. Apply requires only the two core
targets; missing optional native-menu resources are reported and skipped on
other versions/platforms unless that version's declared support profile marks
them required. Candidate extraction requires `workbench.desktop.main.js`.

Full preflight validates every required path and anchor before the write
transaction begins. A future layout change must fail with a specific
missing-path or missing-anchor diagnostic and zero target-file writes.

### Runtime Translation Context

Each candidate node is classified before lookup. Highest precedence wins:

1. `protected-input`: editable controls, current values, and contenteditable
   regions.
2. `protected-editor`: editor, terminal, diff, code, command, path, and log
   surfaces.
3. `protected-conversation`: chat history, Agent output, tool output, and
   user-authored Rules/Skills/Subagents names.
4. `vscode-settings`: Monaco/VS Code settings surfaces handled by the official
   language pack.
5. `model-provider-picker`: model and provider option rows.
6. `cursor-settings`: Cursor-owned Settings navigation and content.
7. `cursor-command-ui`: verified Cursor-owned menus, popovers, dialogs,
   tooltips, and segmented controls.
8. `unknown`: no translation.

The `cursor-settings` classifier is rooted by this deterministic contract:

1. Find a visible `cursor-settings-sidebar-cell-label` node.
2. Its navigation ancestor must contain at least three sibling
   `cursor-settings-sidebar-nav-cell` nodes.
3. The nearest common ancestor must also contain an input whose placeholder or
   accessible label is exactly `Search Settings`.
4. Only that common ancestor and the associated content-pane sibling are
   Cursor Settings roots. A node that merely contains `Settings` is not a root.

The VS Code classifier recognizes the ordinary settings editor through the
stable `.settings-editor`, `.settings-header`, `.settings-toc-container`,
`.settings-body`, and `.setting-item` hierarchy captured in the checked-in
fixture. It takes precedence over Cursor Settings.

Model and provider option text is protected whenever its closest owned
ancestor has role `option`, belongs to a role `listbox`, or is the current value
of the model combobox fixture. The runtime performs whole-node translation,
never substring replacement, in these surfaces. Framing nodes outside option
rows may translate only by an exact dictionary entry whose Chinese value keeps
any model/provider token byte-for-byte. `Auto`, `High`, `Low`, `None`, and
similar enums are protected inside model/provider and technical contexts, but
may translate when the node is a verified natural-language setting label.

A body-level portal is Cursor-owned only when its id is referenced by
`aria-controls` or `aria-owns` from a trigger inside a recognized Cursor root,
or when the active trigger inside that root opens a role `menu`, `listbox`, or
`dialog` during the same mutation turn. Unowned extension/VS Code portals are
`unknown` and skipped.

### Mutation Processing

The runtime performs an initial scan and observes:

- added element and text nodes;
- text-node `characterData` changes;
- `title`, `aria-label`, `placeholder`, `aria-placeholder`, and
  `aria-description` changes;
- owned body-level portals linked to a recognized Cursor trigger.

The current Cursor Settings path does not use Shadow DOM. Shadow Root support
is therefore outside this change. iframe/webview documents also remain outside
the translator. A future build using either boundary fails the supported DOM
contract until a real fixture and bounded observer design are added.

The runtime singleton is stored at
`window[Symbol.for('cursor-v3-chinese-translate.runtime')]`. Loading the same
manifest twice reuses the singleton. Loading a new tool revision disconnects
the previous observer before installing one replacement.

Mutations are deduplicated into a queue of at most 500 nodes and processed at
no more than 120 nodes per animation frame. Overflow clears individual entries
and schedules one rescan of recognized roots only, never `document.body`.
Initial startup may scan `document.body` once to discover roots, but translation
is attempted only after classification. Removed nodes require no cleanup
because node and attribute state is stored in `WeakMap` objects.

Text state records `{source, applied, context}` per node; attributes store the
same tuple per attribute name. A mutation equal to `applied` is a self-write
and ignored. A different value invalidates state and is reclassified, so React
node reuse or an English rewrite is translated again. Chinese output and
unchanged values are no-ops.

The runtime exposes counters only under an explicit test flag: observer count,
queue high-water mark, processed nodes, self-mutations ignored, root rescans,
and translations. Tests require one observer, queue high-water mark at or below
500, and zero additional queued work after two idle animation frames.

### Dictionary Rules

`cursor_translate_dic.txt` retains its current `"source" => "translation"`
format. Blank lines and `#` or `//` comments remain supported. New Cursor 3.11
entries are grouped by Settings page or feature.

Parsing fails on:

- duplicate keys, including duplicates with the same translation;
- conflicting translations for one source key;
- empty keys or values;
- malformed separators or quoting;
- normalized keys that would ambiguously override one another.

Dictionary-key normalization decodes quoted JSON escapes, applies Unicode NFC,
collapses all Unicode whitespace runs to one ASCII space, and trims both ends.
It remains case-sensitive and preserves punctuation. Two distinct source lines
that normalize to the same key are an error even when their translations
match. Runtime exact lookup occurs before normalized lookup.

Dynamic regular expressions remain in one ordered allowlist in code, are
anchored, and have narrow capture groups. Dictionary exact/normalized lookup
runs first, then the first allowed pattern for the classified context wins.
Patterns cover finite numeric/status forms only and are disabled in every
protected context. No expression may match arbitrary sentences, code, paths,
URLs, commands, or user content.

The source-string extractor remains advisory. It never writes the dictionary.
Cursor 3.11 candidates are manually selected from confirmed user-visible UI;
internal identifiers, telemetry keys, stack strings, paths, and source-only
messages are rejected.

## Read-Only Diagnostics

The three diagnostic commands are mutually exclusive with mutating and
extraction modes:

- `--check` answers whether the selected bundle is compatible and safe to
  plan. It reports resolved resources, process state, anchor/checksum validity,
  installation state, and conflicts.
- `--dry-run` includes all `--check` output plus the exact immutable
  `PatchPlan`: create/modify/skip operations, before/after hashes, native-menu
  match counts, manifest location, and write order.
- `--status` validates existing tool manifests and reports `not-installed`,
  `installed`, `drifted`, `needs-recovery`, `stale-after-upgrade`, or
  `legacy-installation`.

They do not create probe files, temporary files, manifests, backups, lock
files, or target writes. They report:

- normalized Cursor path, version, and commit;
- all resolved required files;
- checksum key and whether it is present;
- injection-anchor count and validity;
- current tool marker and manifest state;
- known and unknown conflicting patch evidence;
- whether Cursor is running;
- write-permission metadata;
- the exact planned write set.

Exit codes are stable: `0` for compatible/healthy state, `2` for incompatible
layout or patch conflict, `3` when Cursor is running, `4` for stale or
interrupted state requiring recovery, and `1` for unexpected execution errors.
`--status` returns `0` for `not-installed` and `installed`, and the classified
nonzero code for other states. Missing or upgraded bundles are reported rather
than dereferenced.

Read-only permission reporting uses filesystem metadata and `os.access`; it
does not claim that a later atomic replace is guaranteed. Generated JavaScript
syntax is checked through `node --check -` over stdin. Apply confirms actual
staging-file creation only after all other preflight checks pass and as the
first step of the controlled transaction.

## Transaction and Manifest

### Backup Location

Backups live outside Cursor.app in a tool-owned user-data directory. On macOS:

```text
~/Library/Application Support/cursor-v3-chinese-translate/backups/
```

Windows and Linux use their normal per-user application-data locations. A
bundle identity derived from the normalized application path and product
metadata separates multiple installations. Each apply receives a random
manifest id and its own directory.

The bundle directory contains an atomic `active.json` pointer and at most one
active installation lineage. Completed, rolled-back, restored, and stale
lineages remain immutable audit/recovery records. Backups are retained by
default; the legacy `--keep-backups` flag remains accepted and documents that
behavior. Automatic deletion or pruning is outside this change.

### Manifest Content

The JSON manifest includes:

- schema version, tool name, and tool version;
- manifest id and creation time;
- normalized bundle identity;
- Cursor version and commit;
- every touched path stored relative to `resources/app`;
- original and applied SHA-256 values;
- backup filename and backup SHA-256;
- the exact reversible local patch description;
- pre-existing known patch evidence;
- transaction status: `prepared`, `applying`, `applied`, `rolling_back`,
  `rolled_back`, `restoring`, or `restored`.
- an append-only revision number and optional parent revision;
- a per-operation write journal and the last fsynced transition;
- captured file metadata: mode, uid, gid, flags, timestamps, and extended
  attributes required to restore the original target.

No token, email, user database value, environment dump, or arbitrary command
line is recorded.

The manifest directory is created with mode `0700`; manifest and backup files
use `0600`. Before any plan is accepted, every target is checked with `lstat`
and `realpath`: it must be a regular non-hardlinked file, must not be a symlink,
and both it and its parent must resolve under the selected `resources/app`.
The plan records device, inode, size, hash, and metadata. These values are
checked again immediately before each replace to close the preflight/replace
TOCTOU window. The final Cursor-running check occurs after staging and
immediately before the first target replacement.

Staging starts by copying the target to a same-directory temporary file, then
rewriting its content. This retains mode and copyable metadata before
replacement. The implementation explicitly reapplies mode, owner when
authorized, file flags, timestamps, and all `os.listxattr` values, including
`com.apple.provenance` when present. Metadata capture and comparison are part
of apply/restore tests on macOS.

### Locking and Interrupted-State Recovery

Mutating commands acquire one bundle-scoped exclusive lock in the backup root
using atomic `O_CREAT | O_EXCL`. The lock records only tool/manifest identity,
pid, and creation time. A live owner blocks another apply or restore. A dead
owner does not authorize deletion immediately: the active manifest and journal
must first be classified.

Multi-file replacement cannot be a single filesystem-atomic operation. The
contract is therefore:

- no partial state is returned as success;
- ordinary failures roll back before the command returns;
- a process kill or power loss may leave a journaled mixed state;
- the next mutating invocation performs deterministic recovery before any new
  plan; read-only status reports `needs-recovery` without writing.

For interrupted apply/rollback, recovery requires every target to match either
its recorded original or applied hash and metadata identity. It restores all
targets to the original state from verified backups, verifies them, and marks
the transaction `rolled_back`. Any third value is external drift and blocks
automatic recovery with all evidence retained.

Before restore begins, the tool stores verified pre-restore bytes and metadata
for every planned reverse write. If restore is interrupted, recovery restores
that exact pre-restore state, returning the installation to `applied` or
`drifted`; the user may then retry restore. A restore rollback failure retains
the lock/manifest evidence and reports exact unresolved paths.

### Apply State Machine

1. Resolve the bundle and build the complete read-only preflight report.
2. Acquire the bundle lock and recover any interrupted transaction.
3. Reject a running Cursor process, missing resource, missing checksum key,
   ambiguous injection anchor, legacy installation, stale applied lineage, or
   unsafe conflict.
4. Generate one immutable `PatchPlan` in memory, including final checksum, and
   validate generated JavaScript through `node --check -`.
5. Create the manifest directory and copy every original touched file into it.
   A generated file records an original state of `absent`; a pre-existing
   foreign file at that path is a conflict.
6. Verify each backup SHA-256/metadata snapshot and atomically persist a
   `prepared` manifest plus `active.json`.
7. Stage each final file in its destination directory and fsync content,
   metadata, and parent directory.
8. Revalidate all target identities and verify Cursor is still stopped.
9. Set state to `applying`, then replace targets in stable order while fsyncing
   the operation journal after every replacement. The checksum-bearing
   `product.json` follows workbench content.
10. Verify applied hashes/metadata, HTML marker, generated-script marker and
    manifest id, foreign artifacts, and product checksum.
11. Set state to `applied`, fsync the pointer, and release the lock.

If any action after step 5 fails, the transaction enters `rolling_back` and
restores every target written by that transaction from its verified backup,
including deleting a generated file whose original state was absent. It then
verifies original hashes and metadata and records `rolled_back`. A rollback
failure is reported with exact remaining paths and preserves recovery data.

Repeated apply with an identical active revision is a zero-write no-op. When
the same tool/version and Cursor build has a changed dictionary/runtime, apply
creates a successor revision in the same lineage. The lineage retains the
pre-first-apply originals, while the new revision records current applied
inputs and outputs. Restore always removes the latest tool state and returns
to the pre-first-apply state, subject to the drift rules below.

### Restore State Machine

Restore selects the single active `applied` lineage through `active.json` and
requires matching bundle identity, Cursor version, and commit. Another Cursor
version is `stale-after-upgrade` and rejected before writing. It is retained;
the user must restore against a matching preserved app copy or reinstall from
the official DMG. A new Cursor build receives a separate bundle lineage.

For each file, restore verifies the recorded applied state and reverses only
the tool-owned local patch:

- remove the exact HTML block containing tool name, version, and manifest id;
- delete `cursor_hanhua.js` only if its marker, manifest id, and hash match;
- restore the prior checksum only if the checksum still equals the value
  written by this manifest;
- reverse native-resource replacements only where the exact recorded applied
  bytes are still present.

Drift is classified per file:

- `no-post-apply-drift`: the current file matches this revision's applied hash;
  restore returns it to the pre-first-apply hash and metadata.
- `non-overlapping-post-apply-drift`: exact recorded tool fragments remain
  unique while unrelated bytes differ; restore performs a structured local
  inverse and preserves those unrelated bytes. Its final hash is intentionally
  not required to equal the pre-apply hash.
- `overlapping-or-ambiguous-drift`: a tool fragment/checksum is changed,
  missing, or duplicated; restore performs zero writes and reports conflict.

Pre-existing foreign patches are part of the recorded original. With no
post-apply drift, they are restored byte-for-byte and the original hash is
required. Full-file backups are retained for disaster recovery and
same-transaction rollback, not used to overwrite externally modified files
during normal restore.

All reverse results are generated into one `PatchPlan`, backed up as the
pre-restore state, and staged before replacement. Restore journals each write,
verifies the applicable hash or structured inverse, records `restored`, and
then releases the lock.

### Legacy Tool State

An old `CURSOR_HANHUA_INJECTION`, `cursor_hanhua.js`, fixed `.bak`, or rotated
`.bak.<timestamp>` without a v2 manifest is classified as
`legacy-installation`. The new tool does not adopt, delete, or restore it
because its Cursor version and ownership cannot be proven. Apply stops and
instructs the user to restore with the matching old tool against the matching
Cursor version, or reinstall from the official DMG. Foreign backups remain
untouched.

## Third-Party Patch Coexistence

Coexistence is capability-based, not a claim about every release of another
tool. Detection recognizes this tool's marker separately from foreign marker
names, backup suffixes, injected scripts, renderer hooks, and checksum changes.
It never deletes `.bak`, `backup-*`, or similarly named foreign artifacts.

Known foreign modifications are allowed only when every planned local patch is
unique and reversible. The implementation stops when:

- another tool occupies or duplicates this tool's HTML anchor;
- the intended checksum key is missing or duplicated;
- a native-resource replacement cannot identify exact source bytes;
- an active manifest describes a different current state;
- a restore target no longer contains a unique tool-owned applied fragment.

The supported foreign-patch contract is:

- foreign HTML blocks at a different unique location are preserved;
- arbitrary foreign `product.json` keys and the pre-apply checksum value are
  preserved;
- a modified `workbench.desktop.main.js` is tolerated because it is read-only;
- native-menu resources are changed only through exact unique string-literal
  replacements, each recorded as a reversible fragment;
- already changed, missing, duplicated, or overlapping source fragments stop
  the affected native operation rather than guessing;
- any foreign backup filename or unplanned file is preserved.

Sanitized fixtures are derived from the locally observed 2026-07-13 patch
shapes: `backup-byok-*` artifacts, a foreign workbench injection, arbitrary
product keys/checksum edits, renderer-bundle modification, and
cursor-always-local resources. `tests/fixtures/README.md` records Cursor
version/commit, observation date, retained structural facts, and every removed
private value. It contains no application bundle, user path, token, log, or
account content.

Tests exercise those shapes across `product.json`, `main.js`,
`nls.messages.json`, `workbench.desktop.main.js`, and `workbench.html`.
Untouched foreign markers and backup files must be byte-identical after apply
and restore. Documentation says “verified non-overlapping coexistence” rather
than promising compatibility with every ccursor/Cursor++ version.

## Security and Privacy

The default and only mode in this change is pure localization. The tool reads
only the selected Cursor application resources, its own dictionary, and its
own backup manifests. It does not inspect Cursor user data or make network
requests.

Process detection compares executable path and bundle identity without
printing complete process environments or command lines. Diagnostics redact
unexpected values and never log authentication material. The process check is
repeated immediately before the first replace.

Real UI acceptance uses an isolated temporary user-data and extensions
directory. It does not reuse the normal Cursor profile, account session, chat
history, workspace state, or extension state.

## Testing Strategy

All new behavior follows red-green-refactor. Each regression test is run on the
pre-change implementation or before its production implementation and must
fail for the intended missing behavior.

### Python Unit and Integration Tests

- Cursor 3.11.13 macOS bundle metadata and all supported path entry forms.
- Missing resource, missing checksum key, duplicate anchor, read-only check,
  and running-process preflight failures with zero writes.
- Dictionary duplicate, conflict, malformed-entry, comment, and normalized-key
  validation.
- Manifest creation, schema, version matching, stale-version rejection, and
  status reporting.
- Atomic apply idempotency and exact planned writes.
- Bundle lock contention, dead-owner recovery, interrupted apply recovery, and
  interrupted restore rollback.
- Injected failure after each write boundary followed by complete hash restore.
- Restore of only this tool's changes while preserving foreign modifications.
- Exact conflict rejection when ccursor and this tool target the same fragment.
- Coexistence with representative foreign markers and backup files.

### Runtime DOM Tests

Node 22+, the built-in test runner, and pinned `jsdom@26.1.0` load the generated
runtime against checked-in, sanitized Cursor 3.11 fixture HTML. `package.json`
and `package-lock.json` make the dependency reproducible. Fixture provenance
and sanitization are documented in `tests/fixtures/README.md`. Tests cover:

- Settings sidebar and content translation;
- incrementally inserted nodes;
- `characterData` updates on an existing node;
- React rewriting translated text back to English;
- title, aria-label, placeholder, aria-placeholder, and aria-description;
- menus, popovers, dialogs, tooltips, toggles, and segmented controls;
- bounded dynamic numeric patterns;
- model and provider names remaining unchanged;
- contextual handling of Auto/High/Low/None;
- user input, current input values, code, paths, commands, logs, chat history,
  Agent output, extension names, and custom names remaining unchanged;
- official VS Code Settings fixture remaining unchanged;
- repeated execution and observer callbacks remaining idempotent;
- explicit Shadow Root, iframe, and webview non-support/skip behavior;
- queue bounds and absence of an observer rewrite loop.

### Required Commands

The final verification runs and reports from repository root. `CURSOR_COPY`
is set to the recoverable test application before the final command:

```bash
python3 -m py_compile CursorTranslate.py
python3 -m unittest -v
python3 smoke_test.py
npm ci
npm test
node --check "$CURSOR_COPY/Contents/Resources/app/out/vs/code/electron-sandbox/workbench/cursor_hanhua.js"
```

`npm ci` must leave `package-lock.json` unchanged. Unit tests verify that
`--check`, `--dry-run`, and `--status` do not change the selected bundle,
backup root, repository status, or a monitored temporary directory.

## Real macOS Acceptance

Acceptance is performed on recoverable copies of Cursor 3.11.13, never by
experimenting directly on the primary application. Functional coexistence uses
a copy of the locally patched application. Signature-delta validation uses a
separate pristine copy from the official 3.11.13 DMG when available.

1. Use an isolated user-data and extensions directory with no account session.
2. Record SHA-256 and relevant metadata for `workbench.html`,
   `workbench.desktop.main.js`, `product.json`, `nls.messages.json`, and
   `main.js`; record that `cursor_hanhua.js` is absent or its ownership state.
3. Run `--check` and confirm no hashes or directory contents change.
4. Apply localization and verify the manifest, injected marker, generated
   script, planned writes, and product checksum.
5. Launch the copy and capture visible evidence for the Agents Window, Editor
   Window, Cursor Settings General, Agents, Models, Tools & MCPs,
   Rules/Skills/Subagents, Browser & Network, model menu, and ordinary VS Code
   Settings.
6. Verify expected Chinese labels and descriptions while model/provider names,
   code, paths, user input, and other protected content remain unchanged.
7. Exercise page switches, popovers, and a React rerender. Sample renderer CPU
   once per second for 30 idle seconds before and after apply. The translator
   passes when median CPU rises by less than 3 percentage points, no 5-second
   window averages above 10% solely from idle translation, the queue drains in
   two animation frames, and typing/clicking remains responsive.
8. Quit Cursor completely, run restore, and, with no post-apply foreign drift,
   verify all five recorded hashes/metadata return to their pre-apply values,
   `cursor_hanhua.js` returns to its original absent/owned state, and foreign
   artifacts remain.
9. Launch the restored copy again and verify normal operation.
10. Record signature evidence separately:
    - pristine official copy before apply: baseline `codesign` and Gatekeeper;
    - pristine copy after apply: expected sealed-resource verification failure;
    - pristine copy after restore: result must equal its baseline;
    - already patched coexistence copy: record its pre-existing invalid
      `codesign` baseline and require restore to return to the same result.
      A Gatekeeper result under a machine-wide security override is labeled
      non-evidence, not “accepted by this tool.”

If the exact official DMG cannot be obtained, functional acceptance proceeds
but signature-delta acceptance is explicitly reported as unverified; the
implementation cannot be described as fully manually verified until that gap
is closed.

Redacted screenshots, a page/result matrix, command exit codes, hash/metadata
results, CPU samples, and signature baselines are stored in
`artifacts/manual-verification/` during development. Only a sanitized Markdown

## Acceptance Criteria

- All required automated commands and the DOM suite pass from a clean checkout.
- Read-only modes produce zero filesystem writes.
- Every preflight failure produces zero target writes.
- Injected apply failures restore every original hash.
- Stale manifests and ambiguous conflicts are rejected before writing.
- Normal restore removes only verified tool-owned changes.
- Foreign patch markers, modifications, and backup files survive apply and
  restore byte-for-byte.
- Cursor 3.11.13 Settings and Agents-related pages visibly show the expected
  Chinese translations in real UI evidence.
- Model/provider names, VS Code localization, code, paths, commands, inputs,
  chat history, Agent output, extension names, and custom names are unchanged.
- Restore returns every targeted resource to its recorded pre-apply SHA-256 and
  the restored Cursor copy launches successfully.
- The Git diff contains no application binaries, user configuration, tokens,
  logs, screenshots with private data, or machine-specific absolute paths.
